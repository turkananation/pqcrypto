# Why `pqcrypto` Does Not Claim FIPS 140 Validation

Last updated: 2026-06-05

This document explains, precisely and permanently, why `pqcrypto` states that it
is **not** CMVP/FIPS 140 validated even though it is byte-exact against the
official NIST known-answer tests for ML-KEM (FIPS 203) and ML-DSA (FIPS 204).
Every place in this repository that says "not CMVP/FIPS 140 validated" links
here.

## The two claims are different

There are two distinct, easily-confused claims:

| Claim                                     | Question it answers                                              | What `pqcrypto` has                                                                   |
| ----------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **Algorithm conformance**                 | "Does the math match the FIPS 203/204 standard?"                 | Yes — byte-exact against the checked-in KAT corpora, plus OpenSSL interop for ML-KEM. |
| **Module validation (FIPS 140-3 / CMVP)** | "Is this a *validated cryptographic module* with a certificate?" | No — and it structurally cannot be one as a portable pure-Dart library.               |

Passing the algorithm KATs is necessary but **not sufficient** for FIPS 140.
FIPS 140-3 validates a *module* — a specific, bounded artifact in a specific
operational environment — not an algorithm or a source file.

## What CMVP / FIPS 140-3 validation actually requires

A FIPS 140-3 validation (issued by the NIST/CCCS **Cryptographic Module
Validation Program**, CMVP) requires, at minimum:

1. **A defined cryptographic module** with a precise physical or logical
   boundary, version, and build.
2. **Testing by an accredited laboratory** (a CST lab), not by the vendor, plus
   CMVP review. This is a paid, months-long process that ends in a numbered
   **certificate** on the CMVP Validated Modules list.
3. **CAVP algorithm certificates** for each approved algorithm (ACVP testing) —
   the part `pqcrypto`'s KATs most resemble, but still a formal, separate
   program.
4. **An approved operational environment.** FIPS 140 validates the module on
   specific, named platforms/OS/processor combinations. "Runs anywhere Dart
   runs" is the opposite of a bounded operational environment.
5. **A validated entropy source / DRBG** meeting SP 800-90A/B/C, with an entropy
   justification. `pqcrypto` delegates to `Random.secure()` (the host CSPRNG);
   it ships no validated entropy source and makes no SP 800-90 claim.
6. **A written security policy**, role/service definitions, self-tests
   (power-up known-answer tests, integrity checks), key management, and
   finite-state model documentation.
7. **Ongoing maintenance** (re-validation on change, the CMVP transition
   queues, etc.).

A certificate is the artifact that lets someone say "FIPS validated". Without
that certificate, the phrase is simply inaccurate, regardless of how correct the
code is.

## Why a pure-Dart library cannot, by itself, be a validated module

`pqcrypto` is deliberately a portable, zero-dependency library:

- It runs on the **Dart VM, dart2js, dart2wasm, and Flutter** across Android,
  iOS, web, Windows, Linux, and macOS. FIPS 140 requires a *fixed* operational
  environment, which a "compile-and-run-anywhere" library does not have.
- It performs **no power-up self-tests, integrity check, or finite-state
  enforcement**, and exposes no security-policy-bounded role/service interface.
- It **bundles no validated entropy source or DRBG**; it relies on the host.
- Compilation to JavaScript and Wasm means the executed artifact is generated by
  toolchains outside any validated boundary.

These are design choices that make the library small, auditable, and universal —
and they are exactly the properties a CMVP-validated module is *not* allowed to
have without a great deal of additional, environment-specific machinery.

## What `pqcrypto` therefore claims — and what it does not

**Acceptable (true) wording:**

> `pqcrypto` provides FIPS 203-aligned ML-KEM and FIPS 204-aligned ML-DSA
> implementations that are byte-exact against the checked-in NIST KAT corpora
> and regression suite described in this repository.

**Unacceptable (false) wording — never use these:**

- "FIPS validated" / "FIPS 140 validated" / "FIPS 140-3 compliant module"
- "CMVP validated" / "CAVP certified"
- "certified" / "fully certified"

The distinction is not pedantic: in regulated procurement, "FIPS validated" is a
specific legal/contractual term backed by a certificate number. Claiming it
without one is misrepresentation.

## If you actually need FIPS 140 in production

If your deployment contractually or legally requires a validated module:

1. Use a **CMVP-validated module** for the cryptography (for example, a
   validated OpenSSL provider, platform crypto, or HSM), and treat `pqcrypto` as
   a reference / interop / non-validated path. The ML-KEM
   [OpenSSL interop](OPENSSL_INTEROP.md) evidence is intended to make this
   substitution straightforward.
2. Or pursue your **own CMVP validation** of a module that embeds this code in a
   fixed operational environment with a validated entropy source, self-tests,
   and a security policy. That is a separate, formal effort this repository does
   not undertake.

## Summary

`pqcrypto` gives you strong, reproducible **algorithm-conformance evidence**
(KATs, interop, cross-platform tests). It does not — and as a portable pure-Dart
library cannot — give you a **FIPS 140 module validation**. Those are different
things, and this repository is careful to claim only the first.
